## 决策 001：5 种核心玩法原型作为第二层分类，与 12 母型并存

- **日期**：2026-06-14
- **问题**：如何从编辑器架构角度扩展站点的分类体系？
- **选项**：
  1. 用 5 种核心原型替代 12 母型
  2. 把 5 种核心原型作为独立维度与 12 母型并存
  3. 把 5 种核心原型仅用于 Demo 模板，不在站点导航中展示
- **决定**：选项 2 —— 12 母型（玩家感受） + 5 核心原型（编辑器架构）双层分类并存。
- **原因**：
  - 12 母型面向学习者，提供"这是什么玩法"的锚点
  - 5 核心原型面向实现者，提供"底层循环和数据结构是什么"的锚点
  - 两者互补，不互相替代
- **影响**：
  - `PlayMeta` 新增可选字段 `pattern`
  - 首页筛选新增"核心原型"分组
  - 母型详情页需要显示所属核心原型
  - 版主发帖表单增加核心原型选择

## 决策 002：5 种核心原型的具体定义

- **日期**：2026-06-14
- **问题**：5 种核心原型的边界如何划分？
- **决定**：
  1. **action** — 动作敏捷：Input → Avatar → Physics → Score
  2. **spatial** — 空间布局：Board → Cell → Rule → State Change
  3. **merge** — 合成成长：Resource → Merge → Level Up → Production
  4. **management** — 经营模拟：Building → Production → Economy → Growth
  5. **strategy** — 数值策略：Unit → Stats → Combat → Reward
- **原因**：这 5 种循环覆盖了绝大部分小游戏的编辑器数据结构；每个原型的抽象节点都对应可实现的 Demo 模板。
- **影响**：
  - Demo 模板按这 5 种循环设计
  - 版主选择原型后，自动生成对应循环的 breakdown 骨架

## 决策 003：先实现数据模型与筛选，再补 Demo

- **日期**：2026-06-14
- **问题**：实施 5 种核心原型的优先级如何安排？
- **决定**：分 3 个迭代：
  1. 迭代 1：数据模型 + 首页筛选 + 版主表单
  2. 迭代 2：母型映射 + 页面展示
  3. 迭代 3：5 个核心原型最小 Demo
- **原因**：让分类体系先 selectable/filterable，版主能先用起来；Demo 可以后续逐步补齐，不影响内容生产流程。
- **影响**：迭代 1 完成后，内部即可开始按核心原型发帖和筛选。

## 决策 004：核心原型元数据以代码常量为主，文案可后续迁移到 content/

- **日期**：2026-06-14
- **问题**：核心原型元数据放在代码里还是 content/ 目录？
- **选项**：
  1. 像母型一样放在 `content/patterns/<key>/meta.json`
  2. 放在 `src/lib/patterns/patterns.ts` 作为稳定常量
- **决定**：选项 2 作为第一阶段实现；后续如果版主需要在线编辑原型文案，再迁到 `content/patterns/`。
- **原因**：5 种核心原型是架构层的稳定分类，不频繁变动；代码常量实现更快，类型更安全。
- **影响**：当前无需新增 content 读取逻辑；后续迁移成本低。

## 决策 005：OVO 伞品牌架构下的 GamesLog 品牌露出规则

- **日期**：2026-09-08
- **背景**：OVO（"原子"）为所有项目的母品牌；gameslog.top 是内容媒体站，ovoforge.com 是工具站集合（当前为 Pixel Studio）。完整架构见 ovo_system `docs/brand-architecture.md`。
- **决定**：
  1. 搜索位（title 后缀 / H1 / meta description）只出现 **GamesLog**——title 后缀统一为 `- GamesLog`（现存 `- OVO` 后缀属待修复项）。
  2. 背书位（页脚 / 关于页）出现 `An OVO Project` 母品牌背书。
  3. 与 ovoforge.com 工具站的互导只做编辑式上下文导流（文章 ↔ 工具的自然互链），禁止强制跳转/横幅互导；导流落地暂缓，等 Pixel Studio 具备向生产线供素材能力后再做。
- **原因**：搜索位混用母品牌会稀释 GamesLog 品牌词建设；分域名让内容站（信息型关键词）与工具站（工具型关键词）各自积累权重。
- **影响**：SEO 修复任务（双 H1 / title 后缀）以本决策为准；英文化工作不受品牌规则影响。

## 决策 006：可玩 demo 公开通道统一为「自包含静态包进站点仓库 + release 产物分支」

- **日期**：2026-09-30
- **问题**：文章/母型页的可玩 demo 以什么形式公开托管？历史上存在三种并存形态：自包含静态包打进 `public/embed/plays/`、外部平台托管（1022 平台包）、localhost 动态预览直连（`127.0.0.1:19527/preview-assets/...`）。
- **选项**：
  1. 外部平台/R2 托管（站点仓库不带大文件）
  2. 自包含静态包统一打进站点仓库（`public/embed/plays/{slug}/`、`public/demos/atomic/{key}/`），随 `pnpm release` 进入 deploy/gameslog.top 产物分支
  3. 维持现状混用
- **决定**：选项 2。所有可玩 demo 必须是自包含静态包（零 runtime-gateway 依赖、零 localhost），经 ovo_system `scripts/export-static-demo.ts`（v2 项目）或 AtomCore 单文件（母型原子 demo）产出；localhost/外部托管引用视为发布缺陷必须清零。
- **原因**：单包 0.8~3.3MB 对 git 与产物体积均可接受；deploy 分支通道已存在且被验证（服务器 `bash deploy.sh deploy` 免构建生效）；零外部依赖 = 线上可玩性与本地验证完全一致，无第二真相源；R2/三方托管在当前资产规模下是纯增加运维面。
- **影响**：tic-tac-toe-showdown 的 localhost 引用已清零（content/ 全目录 grep 通过）；未来大资产（>10MB）再评估 R2；已落地：14/14 母型原子 demo + 11 篇可玩 demo 案例全部走本通道。
