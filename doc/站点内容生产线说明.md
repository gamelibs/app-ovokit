# 站点内容生产线设计说明（存档副本）

> 本文档为 ovo_system `docs/site-content-production-line.md` 的存档副本，**权威版本以 ovo_system 为准**；若两侧不一致，以 ovo_system 版本为准并同步本文件。
> 日期：2026-09-06　状态：已实施（M0/M1/M2 已落地验收，M3 未启动；实施记录见 ovo_system 权威版 §10/§11）

---

## 对站点侧的含义（速读）

- 内容生产线建在 **ovo_system（生产端）**，本仓库永远只负责渲染，不引入选题/生成/审核逻辑。
- 站点与生产线之间唯一的契约是 **ContentPack**（见 §4），经 `gameslog-mdx-adapter` 物化为 `content/plays/{slug}/article.mdx + meta.json`。
- 站点侧需要配合的只有：保持 `content/*` 内容模型稳定；`/mod` 后台仅限运维功能，不长生产功能。

---

## 1. 背景与内容模型

### 1.1 内容模型：双层结构（Pillar + Cluster）

站点内容**不是**按游戏样本逐个写稿，而是：

- **框架层（常青，写一次长期吃权重）**：以 14 个行为母型/机制为骨架（taxonomy 现值；早期"12"已过时，本站现有 12 个母型页，缺 merge-unit / turn-duel），讲清"这类玩法的规则循环是什么、为什么好玩、关键设计点在哪"。对应本站 `/archetypes` 页面群。
- **案例层（实例流，可无限更新）**：每篇文章拿一个具体游戏开刀——它用到哪些母型、怎么组合、参数怎么调——附可试玩 Demo，并**链接回母型页**。对应本站 `/play/{slug}` 文章 + `/embed/` 试玩。
- **权重回路**：案例页给母型页输内链权重；母型页随案例增多越来越权威。4000+ 游戏库 = 近乎无限的选题池；"同一母型在不同游戏中的变体"本身也是选题。

### 1.2 行业验证（该模型已被反复跑通）

- **SEO 领域**：HubSpot 的 Pillar Page + Topic Cluster 模型。
- **知识领域**：Pattern Language（模式语言），源头是建筑学《A Pattern Language》（Christopher Alexander，253 个模式 + 真实案例）。
- **游戏行业同类**：Game Programming Patterns（gameprogrammingpatterns.com）、ncase.me / Explorable Explanations（文章内嵌可玩 Demo 的开创者）、Game Maker's Toolkit（机制先行 + 案例佐证）、Deconstructor of Fun（统一框架拆手游）、Lost Garden（玩法原子/grammar）。
- **其它行业同构**：Laws of UX、Mobbin、ui-patterns.com（UX）、Refactoring.Guru / patterns.dev（编程）、Hooktheory Theorytab（乐理框架 + 逐首歌分析，回链结构与我们一致）、Salt Fat Acid Heat（烹饪）、Every Frame a Painting（电影）。

### 1.3 结论

模型成立。产线设计必须**机制驱动选题**（从母型出发筛游戏），而非"哪些游戏值得写"。

## 2. 职责边界（硬性）

| 侧 | 归属 | 职责 | 禁止 |
|---|---|---|---|
| 生产端 | ovo_system | 选题、生成、审核、发布、回流分析 | 不得包含任何站点渲染细节 |
| 展示端 | 各站点仓库（含本仓库） | 渲染 ContentPack 物化后的内容文件 | 不得包含生产逻辑；`/mod` 后台仅运维（评论/配置） |
| 契约 | ContentPack | 两侧之间唯一允许交换的数据结构 | 禁止绕过契约直接读对方内部数据 |

成熟参照：WordPress `wp-admin` vs 主题；Headless CMS（Contentful/Sanity/Strapi）+ Next.js；Content-as-code（Decap/Tina 生成 git commit）。三条路形态不同，规则相同：**展示端是哑的，生产端不知道展示细节**。

## 3. 总体架构：四层插件 + 注册表 + 状态机

```
┌─ 选题源（可插拔）────────────────────────────────┐
│  母型驱动选题 / 趋势选题 / 手动选题 …              │
├─ 生成器（可插拔）────────────────────────────────┤
│  forge-studio 本地模型 / 外部 API / 人工录入       │
├─ 质量门禁（可插拔）──────────────────────────────┤
│  事实校验 / 查重 / SEO 完整性 / 结构字数 / Demo可用 │
├─ 发布渠道（可插拔，核心隔离点）──────────────────┤
│  gameslog-mdx-adapter / 未来站点X-adapter …       │
└─ 内容契约（唯一定义点）──────────────────────────┘
   ContentPack：标题/正文/母型引用/Demo引用/素材/SEO
```

- **四层各自是插件**：选题源、生成器、门禁、渠道适配器均可独立增删替换，互不感知实现。
- **注册表**：插件按 manifest 注册（id / 版本 / 输入输出 / 能力声明），管理端可装卸启停。
- **管线状态机**：

```
topic(候选选题) → draft(草稿) → review(待审) → approved(已通过)
   → published(已发布) → feedback(回流：收录/阅读/表现) → archived(归档)
```

- 每个状态迁移留审计记录；发布失败可重试，不丢草稿。

## 4. ContentPack Schema v1（契约，唯一定义点）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 管线内部唯一 id |
| `slug` | string | URL slug，渠道内唯一 |
| `title` | string | 标题 |
| `summary` | string? | 摘要/导语 |
| `bodyMarkdown` | string | 正文（Markdown，引擎层不规定 MDX 组件） |
| `archetypeRefs` | string[] | 母型引用（taxonomy id），cluster 回链依据 |
| `patternRefs` | string[]? | 玩法原型引用 |
| `demoRef` | object? | `{ gameId, demoId? }` 试玩引用 |
| `assets` | object[]? | 素材清单（cover/插图，类型 + 来源路径） |
| `seo` | object | `{ description, keywords[], canonical? }` |
| `lang` | string | 语言（默认 zh-CN） |
| `status` | string | 管线状态机状态 |
| `createdAt/updatedAt/publishedAt` | ISO 时间 | |
| `channelMeta` | object? | 渠道私有附加字段，**引擎不解释、不校验** |

规则：

- schema 变更必须 bump version 并同步本文档（权威版在 ovo_system）。
- 新字段向后兼容；渠道私有需求只能进 `channelMeta`，禁止污染公共字段。

## 5. 渠道与适配器

### 5.1 ChannelProfile（每站点一份 JSON 配置）

```jsonc
{
  "channelId": "gameslog-main",
  "siteRef": "becf127c-e6b3-44c1-9ea2-2939ad5583a1",
  "adapterId": "gameslog-mdx",
  "repoPath": "../../ovo/gameslog-site",
  "contentDir": "content/plays",
  "gates": ["dedup", "seo-fields", "structure"],
  "autoRelease": false,
  "enabled": true
}
```

多站点 = 多份 profile，**引擎代码零改动**。

### 5.2 适配器接口

```ts
interface ChannelAdapter {
  validate(profile: ChannelProfile): Promise<CheckResult>;
  publish(pack: ContentPack, profile: ChannelProfile): Promise<{ ref: string; url?: string }>;
  unpublish(ref: string, profile: ChannelProfile): Promise<void>;
  status(profile: ChannelProfile): Promise<{ publishedRefs: string[] }>;
}
```

### 5.3 gameslog-mdx-adapter（首个实现）

- `publish`：写 `content/plays/{slug}/article.mdx` + `meta.json`，素材拷入 `public/plays/{slug}/`；`autoRelease=true` 时触发 `pnpm release`（产物构建 + 本地实例重启，远端部署仍由服务器侧 `deploy.sh update` 完成）。
- `meta.json` 字段映射写入 `channelMeta`（待核实现有结构后定稿）。
- 站点细节只允许存在于适配器内；**引擎层禁止出现**。

## 6. 数据存储（生产端）

- SQLite，沿用 ovo_system `scripts/local-agent-bridge/lib/analysis-db.mjs` 的封装模式，不引入新数据库。
- 表：`content_topics` / `content_drafts` / `content_packs` / `channel_profiles` / `publish_records` / `pipeline_runs`；审计复用 `audit_log`。

---

## 7. 反硬编码规则（实施审查清单）

1. 引擎层禁止出现任何站点名、域名、仓库路径字面量。
2. 渠道差异只允许存在于适配器目录与 profile JSON。
3. ContentPack 是唯一跨层数据结构；适配器禁止反向读引擎内部表。
4. 插件注册/装卸不得需要改引擎代码。
5. gameslog 是第一个渠道，不是唯一渠道——任何"只支持一个站点"的实现都视为缺陷。

## 8. 分期实施路线

| 期 | 内容 | 验收 |
|---|---|---|
| M0 | ContentPack schema + gameslog-mdx-adapter + 手工通路 | 人工 ContentPack 一键发布到 content/plays/ 并构建成功 |
| M1 | 母型驱动选题器：taxonomy × 分析库产选题队列 | 选题队列可持续产出，去重正确 |
| M2 | 生成器（本地模型）+ 质量门禁 + 审核台 | AI 草稿过门禁、人工审后可发布 |
| M3 | 第二个渠道适配器（验证插件化主张） | 新站点接入不改引擎 |
