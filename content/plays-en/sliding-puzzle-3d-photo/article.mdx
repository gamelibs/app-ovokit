# Slider Puzzle: Turning "Playable Showcase" into a Reusable Demo

## One-Sentence Essence

On the surface, it's randomly shuffling image tiles; actually, the core mechanism is executing N valid moves in reverse from a "completed state"; this article focuses on explaining how this method naturally guarantees solvability and controls difficulty.

The value of this gameplay lies in: **rules are extremely easy to understand** (as long as you can move puzzle tiles), but gaps can be pulled apart through "feel and presentation."

## Rules (Minimum Closed Loop)

1. Slice an image into a `W×H` grid, leaving 1 empty space
2. Player click/drag: only allow tiles adjacent to the empty space to move into it
3. When all tiles return to their initial positions → Victory settlement

## Delivery Suggestions (Making an Embeddable Demo)

- **Interaction and page isolation**: Use `/embed/*` + iframe to avoid scroll/gesture interference
- **Strong mobile adaptation**: Place buttons in an outer toolbar, stage fills 100% of the container
- **Future expansion**: Level atlas, different grid sizes, timer/steps, hints, and shuffling strategies

---

## 1) Shuffling: The biggest pitfall to avoid is ensuring "Solvability"

The slider puzzle (15-puzzle) is not solvable for all permutations.

If you shuffle randomly, you often encounter:

- Players can't solve it no matter how they play (experience disaster)
- You have to add "Skip/Reset", but this weakens the credibility of the gameplay

A more stable engineering approach is:

- Start from the "completed state"
- Randomly make N valid moves (equivalent to the player operating in reverse)
- The resulting state is **naturally solvable**

This also makes it easy for you to control difficulty: the larger N is, usually the harder it is (though not strictly linear).

---

## 2) Input Feel: Both Click and Drag Must Be "Explainable"

Mobile devices commonly have two types of input:

- **Click**: Tap a tile; if it's adjacent to the empty space, move it
- **Drag**: Drag towards the empty space direction; if conditions are met, slide it in

Key points for feel:

- **Moveable Highlight**: Only highlight tiles "adjacent to the empty space", so players won't get lost
- **Elastic Feedback**: If dragging in the wrong direction, snap back (and optionally provide slight vibration/sound)
- **Move Rhythm**: Suggested move duration is `120~200ms` (too slow feels sticky, too fast lacks feel)

---

## 3) Victory Judgment: Don't Use "Does the Picture Look Like It", Use Index Alignment

The most stable method to judge victory is:

- Each tile has a `homeIndex` (the position it should be in when completed)
- If the `index` of the current cell equals the tile's `homeIndex`, it's correct
- The empty space does not need judgment

This way, you don't rely on the rendering layer, and won't be affected by 3D/perspective.

---

## 4) 3D Perspective and Animation: Create "Premium Feel" with Minimum Cost

You don't need complex 3D scenes; common "sufficient" feel enhancements include:

- **Slight Perspective**: The stage has a fixed tilt angle overall
- **Lighting/Shadows**: Makes tiles look like they have "thickness"
- **Hover/Press**: Moveable tiles lift slightly when pressed
- **Slide Tween**: Use easing to make the slide smoother

Note: The purpose of animation is not to show off skills, but to "explain rules" and "enhance feedback."

---

## 5) Delivery Checklist for a Reusable Demo (For Site Embedding)

To make it a site-reusable embed Demo, it is recommended to include:

- [ ] **Parameters**: Grid size (3×3/4×4), shuffle steps N, whether to show steps/timer
- [ ] **Controls**: Restart/Shuffle/Hint (optional)
- [ ] **Adaptation**: Mobile does not steal scroll (suggest iframe + `touch-action` strategy)
- [ ] **Reset**: Support `postMessage({type:"demo:restart"})` or reload

## Boundary Conditions

- Must start by randomly moving from the "completed state"; strictly prohibit directly randomly arranging all tiles, otherwise unsolvable states will appear.
- When the player clicks or drags, only allow tiles adjacent to the current empty space to move; invalid operations must be given elastic feedback.
- Victory judgment strictly relies on whether each tile's `index` in the grid equals its preset `homeIndex`, completely ignoring visual rendering differences.
- Mobile requires gesture isolation via an outer toolbar and iframe to prevent page scroll interference with game dragging operations.
- Animation parameters (such as move duration) must be controlled within the `120~200ms` range; too slow feels sticky, too fast lacks feel.

## Design Trade-offs

- **Benefit**: Generating levels by "moving in reverse from the final state" ensures 100% solvability, eliminating the need for extra logic to handle unsolvable states.
- **Cost**: The initial state after shuffling is fixed (i.e., the final state); players cannot experience the process of exploring from a completely chaotic state.
- **Alternative**: If forced to use random arrangement, although the initial state is more "chaotic", it leads to a large number of unsolvable states, forcing developers to add "Skip/Reset" functions, thereby weakening gameplay credibility.
- **Benefit**: Using `index` vs `homeIndex` comparison for victory judgment results in simple logic and is unaffected by 3D perspective or rendering layers.
- **Cost**: This judgment method completely strips away the intuitive feeling of "does the picture look like it" at the visual level, increasing the abstraction degree of code implementation.
